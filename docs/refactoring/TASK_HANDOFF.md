# Передача задач между агентами StitchVue

Минимальный workflow без оркестратора. Все задачи — файл по шаблону [`TASK_TEMPLATE.md`](TASK_TEMPLATE.md).

`status: approved` — необходимое, но **недостаточное** условие. Разрешение проверяется скриптом **до серии записей и после diff**. Промпт агента не блокирует инструменты: изоляция файлов обеспечивается `allowed_paths` + `refactor-task-check`, а не текстом чата.

## Маршруты (не все агенты на каждую задачу)

Coordinator нужен для первичной карты и **межмодульных** зависимостей (IPC, общие контракты). Для локального этапа его не запускать.

### Low

План + TASK (decomposition опционален, если scope очевиден) → пользователь `approved` → executor + адресные тесты.

Guardian не обязателен, если diff строго в `allowed_paths` и нет хуков/эффектов/IPC.

### Medium

Decomposition → `approved` → executor → **regression-guardian**.

### High

**code-auditor** (узкий модуль) → TASK + `approved` → executor → guardian → **ручной smoke** из § «Сценарии регрессии».

Обязательны изолированные fixture-каталоги. Запрещены операции над пользовательскими фото, избранным на диске и боевой SQLite.

## Классификация риска (по инвариантам, не по числу файлов)

| Риск | Примеры | Проверка |
|------|---------|----------|
| **low** | Чистые функции, типы, константы, перенос без смены поведения и без React state | Параметризованные тесты границ **до/вместе** с переносом, `--strict` |
| **medium** | React hooks, состояние, `useEffect`, подписки, async lifecycle | Тесты + guardian |
| **high** | Файловые операции, SQLite, IPC, сессии каталога, thumbnail scheduler | Auditor + тесты + guardian + ручной smoke |

Извлечение `directorySession` (и любой логики сессии/инвалидации/очереди событий Tauri) — **минимум medium**, пока не доказано полное сохранение порядка эффектов и отмены. Не считать low из‑за «это всего лишь хук».

Повышение риска: если этап затрагивает отмеченный инвариант из `.cursor/rules/business-invariants.mdc` — не ниже medium; ФС/IPC/SQLite/миниатюры — high.

## Цепочка по роли

1. **architecture-coordinator** — только карта границ и конфликтующие контракты; черновик TASK (`draft`), гипотезы не как требования.
2. **frontend-decomposition** / **backend-decomposition** — уточнение scope, инварианты, тесты; для low можно пропустить, если план уже однозначен.
3. Пользователь: `status: approved`, `base_commit: $(git rev-parse HEAD)`, глазами «должно остаться неизменным», затем `--seal` (печать контракта). Смена `allowed_paths` / §2–4 после печати требует снова `approved` + `--seal`.
4. **frontend-executor** / **backend-executor** — гейты ниже. `in_progress` не разрешение: старт только из `approved` с валидным `approval_hash`.
5. **regression-guardian** — medium и high; low — если diff не локальный или риск занижен.

**code-auditor** — вне исполнения; high до правок или по запросу. Не дублировать decomposition.

## Три гейта исполнения

Скрипт: `node scripts/refactor-task-check.mjs <task>`.

| Когда | Команда | Смысл |
|-------|---------|--------|
| Утверждение | `--seal` | только `status: approved`: пишет `approval_hash` по YAML-scope + §2–4. Исполнитель **не** вызывает `--seal` |
| До любой записи | `--preflight` | **только approved** + совпадающая печать + чистые `allowed_paths` + валидный `base_commit` |
| Перед каждой серией Write | `--auth` | `approved` или `in_progress` **и** тот же `approval_hash`. Сам `in_progress` не доказательство |
| После изменений | `--strict` | diff ⊆ `allowed_paths` (+ файл задачи) + печать; затем `--run-tests` |

Статусы: `draft` → `approved` (`--seal`) → `in_progress` → `verification` → `completed`. Нельзя `draft` → `in_progress`.

Файл задачи в scope (смена статуса). Расширение `allowed_paths` ломает hash → FAIL, пока повторный `--seal` после вашего `approved`.

Незакоммиченные файлы вне scope и расхождение HEAD/`base_commit` — на preflight. Если TASK есть в `base_commit`, контракт рабочей копии должен совпадать с git.

### Неизменяемый контракт после `--seal`

`approval_hash` считается по YAML (`allowed_paths`, `forbidden_paths`, `tests`, …) и телу **§2–§4** (от `## 2. Scope` до `## 5. Rollback`). После успешного `--seal` **запрещено** менять §2–§4, в том числе чекбоксы ручного smoke в §4.

- Результаты smoke и финальный отчёт — только **§7** или отдельный отчёт вне hash-контракта.
- Смена `status` в frontmatter, §1, §5–§7 **не** входит в печать, но правки §2–§4 ломают `--preflight` / `--auth` / `--strict` (lint: «печать устарела»).
- Нужны новые scope или критерии приёмки → `status: approved`, правки §2–§4, снова `--seal`, затем исполнение. Не маскировать это правками при `completed`.

Пример расхождения после закрытия без соблюдения правила: TASK-2026-003 (см. [`HISTORY_REWRITE_2026-10-16.md`](HISTORY_REWRITE_2026-10-16.md)).

## Защита пользовательских данных

- Никаких copy/move/delete/rename над каталогами пользователя из агента или тестов.
- Backend-тесты — только временные fixture-директории и тестовая БД.
- High-risk задача без явного запрета на пользовательские пути — не `approved`.
- Оригиналы фото не удаляются и не перезаписываются вне явной user-операции в продукте (инвариант); рефакторинг это не меняет.

## Сценарии регрессии (smoke)

Не гонять все после каждого low-этапа. Обязательно: перед релизом, после серии связанных этапов, после **любого high**, и выборочно после medium по затронутым инвариантам.

1. Быстрое переключение папок не показывает фотографии предыдущей.
2. Сортировка сохраняет ожидаемый порядок.
3. Скролл и загрузка миниатюр не блокируют интерфейс.
4. Добавление в избранное не изменяет оригинал.
5. Удаление и перемещение не затрагивают файлы вне выбранного набора.
6. Переименование папки избранного соответствует утверждённой бизнес-логике.

В задаче (§4) указать, какие пункты применимы; для low часто «N/A».

## Бюджет исследования (токены)

- Сначала символы и импорты, затем узкие диапазоны. Файлы ≫ 400 строк не читать целиком без обоснования.
- Не более **двух** итераций самостоятельного поиска первопричины; дальше — стоп.
- Расширение scope — стоп, не «заодно».
- Отчёт исполнителя/guardian/auditor: **300–500 слов**, если нет P0/P1. Без больших фрагментов кода.
- Исполнителю — путь к файлу задачи, не roadmap. Guardian — путь, diff от `base_commit`, отчёт исполнителя.
- Не запускать субагентов без прямой просьбы пользователя. Не повторять аудит неизменённых участков.

## Команды

```bash
git rev-parse HEAD
node scripts/refactor-task-check.mjs docs/refactoring/tasks/TASK-....md --seal
node scripts/refactor-task-check.mjs docs/refactoring/tasks/TASK-....md --preflight
node scripts/refactor-task-check.mjs docs/refactoring/tasks/TASK-....md --auth
node scripts/refactor-task-check.mjs docs/refactoring/tasks/TASK-....md --strict
node scripts/refactor-task-check.mjs docs/refactoring/tasks/TASK-....md --strict --run-tests
node --test scripts/refactor-task-check.test.mjs
```

Перенос чистой функции: `--strict` недостаточен. Нужна таблица входов (границы интервалов, `null`/`undefined`, нули, отрицательные, `NaN` если тип это допускает) с тем же оператором сравнения, что в исходнике (`<=` нельзя тихо заменить на `<`).
