# StitchVue — как выпускать версии

Памятка для сопровождающего. Не каждый коммит — релиз. Релиз = осознанный тег + артефакты на GitHub.

Связанные материалы: [`RELEASE_READINESS_AUDIT.md`](./RELEASE_READINESS_AUDIT.md), [`RELEASE_FOUNDATION_REPORT.md`](./RELEASE_FOUNDATION_REPORT.md), spec [`002-stitchvue-release-auto-update`](../../specs/002-stitchvue-release-auto-update/spec.md).

---

## Политика версий (важно)

| Статус | Версия / тег | Кому | GitHub Release |
|--------|--------------|------|----------------|
| **Сейчас** | **`0.1.0`** / `v0.1.0` | Узкий круг тестировщиков | **Pre-release** (не Latest для широкой аудитории) |
| Позже | `0.1.x` / `0.2.x` | Тот же круг + расширение | Pre-release, пока нет объявления |
| Публичный Latest | первая «объявленная» сборка с рабочим updater | Все | Обычный Release, помечен **Latest** |

**`0.1.0` — первая версия для закрытого тестирования**, не первый массовый публичный выпуск.

- Тестеры получают ссылку на конкретный Release / asset (`.exe`), а не «скачай Latest с главной».
- Пока CI/updater не готовы, установщик можно собрать локально и приложить к Pre-release вручную.
- In-app «Проверить обновления» для круга тестеров имеет смысл только после появления подписанных артефактов и `latest.json` (см. spec 002). До этого — ручная переустановка NSIS.
- **Не** помечать Pre-release как Latest, пока владелец явно не решит открыть выпуск широкой аудитории (CL-R01 / CL-R05 в spec 002).

Формат номера: [SemVer](https://semver.org/) `MAJOR.MINOR.PATCH` (пример: `0.1.0`). До `1.0.0` ломающие изменения в минор/патч допустимы, но номер всё равно должен совпадать во всех трёх файлах и в git-теге.

## Перед любым выпуском (чеклист)

1. **Рабочее дерево** — нет незавершённых экспериментальных правок, которые не должны попасть в EXE. `git status`, `git branch --show-current`.
2. **LICENSE** — файл [`LICENSE`](../../LICENSE) в корне (MIT). Без него не объявлять публичный Latest (CL-R05).
3. **Версии синхронизированы** в трёх местах и равны тегу без префикса `v`:
   - `package.json` → `"version"`
   - `src-tauri/Cargo.toml` → `version`
   - `src-tauri/tauri.conf.json` → `"version"`
4. **Проверки качества** (минимум):
   ```text
   npm run typecheck
   npm test
   npm run i18n-check
   cargo test --manifest-path src-tauri/Cargo.toml
   ```
5. **Локальная сборка установщика** (когда нужна проверка до CI):
   ```text
   npm run tauri build
   ```
   Ожидаемый артефакт:
   ```text
   src-tauri/target/release/bundle/nsis/StitchVue_<version>_x64-setup.exe
   ```
6. **Smoke на Windows** (фото пользователя не трогать тестовыми delete/move вне продукта):
   - установка / запуск;
   - открыть папку с изображениями;
   - миниатюры, избранное, локальная корзина (если в scope выпуска);
   - данные приложения только в `%LOCALAPPDATA%\StitchVue\` — не рядом с оригиналами фото;
   - при обновлении/переустановке каталоги фото и `%LOCALAPPDATA%\StitchVue\` не должны «обнуляться» установщиком (обновляется только приложение).

## Как повысить версию

1. Решить SemVer (для закрытого круга после `0.1.0` обычно `0.1.1` = фикс, `0.2.0` = заметная функция).
2. Обновить **одновременно** три файла выше.
3. Кратко описать изменения в теле GitHub Release (и позже — в `latest.json` `notes`, когда появится updater).
4. Закоммитить bump отдельным коммитом, например: `chore(release): bump version to 0.1.1`.

Пока нет скрипта синхронизации — сверять глазами или `rg '"version"|version =' package.json src-tauri/Cargo.toml src-tauri/tauri.conf.json`.

## Как создать тег и Pre-release (закрытый круг)

Тег всегда с префиксом `v`, номер = версия приложения:

```text
git tag -a v0.1.0 -m "StitchVue 0.1.0 — closed testing"
git push origin v0.1.0
```

На GitHub:

1. Releases → Draft a new release (или дождаться workflow по тегу, когда CI появится).
2. Выбрать тег `v0.1.0`.
3. Заголовок: `StitchVue 0.1.0 (closed testing)`.
4. Прикрепить `StitchVue_0.1.0_x64-setup.exe` (и позже `.sig` / `latest.json`).
5. Включить **Set as a pre-release**.
6. **Не** включать «Set as the latest release».
7. Publish release → отправить тестерам прямую ссылку на Release или asset.

Черновик (Draft) тоже допустим: виден только тем, у кого есть доступ к репозиторию.

## Где лежит готовый EXE

| Источник | Путь / URL |
|----------|------------|
| Локальная сборка | `src-tauri\target\release\bundle\nsis\StitchVue_<ver>_x64-setup.exe` |
| GitHub (после публикации) | `https://github.com/PavelKull/StitchVue/releases/tag/v<ver>` |
| CI (когда будет) | артефакты job → upload в тот же Release |

Имя файла задаёт Tauri NSIS; не переименовывать произвольно, если уже завязан updater URL.

## Если публикация не удалась

| Симптом | Что делать |
|---------|------------|
| Тег запушили, Release пустой / workflow упал | Смотреть Actions logs; исправить; **не** помечать битый релиз Latest. Можно удалить draft/pre-release и перезалить assets на тот же тег **или** сделать новый patch-тег (`v0.1.1`). |
| Неверный номер версии в EXE | Пересобрать после синхронизации трёх файлов; новый тег с правильной версией. Не полагаться на «почти тот же» тег. |
| Нет секрета подписи updater | Не публиковать updater-артефакты как Latest; для закрытого круга можно временно раздавать только NSIS без in-app update. |
| Случайно пометили Latest | В Release settings снять Latest / сделать Pre-release; при необходимости указать другой тег как Latest. |

## Как отменить неудачный выпуск

1. **Не установлен широко** — удалить GitHub Release (или оставить Pre-release с пометкой в notes «superseded»), при необходимости удалить тег:
   ```text
   git push origin :refs/tags/v0.1.0
   git tag -d v0.1.0
   ```
   Затем выпустить исправленный тег (часто новый patch: `v0.1.1`), чтобы не путать уже скачавших `v0.1.0`.
2. **Уже стоит у тестеров** — не «отзывать» с их дисков; выпустить следующий Pre-release с фиксом и попросить обновиться (вручную или через updater).
3. **Никогда** не `git reset --hard` / force-push в `main` ради отмены релиза — только теги/Releases и новый номер версии.

Фотографии и `%LOCALAPPDATA%\StitchVue\` откат релиза **не** удаляет; риск только если пользователь сам снёс папку app data или удалил файлы через функции приложения.

## После появления CI/CD и updater (краткий ориентир)

Когда будут workflow и `tauri-plugin-updater` (spec 002):

1. bump трёх версий → push тега `vX.Y.Z`;
2. CI собирает NSIS, подписывает, кладёт `.exe`, `.sig`, `latest.json` в Release;
3. для закрытого круга — Pre-release + прямая ссылка; endpoint updater настроить так, чтобы тестеры видели нужный канал (или тестировать парой версий по spec § Verification);
4. публичный Latest — отдельное решение владельца, с LICENSE, рабочим updater и smoke двух версий.

До готовности CI этот файл остаётся источником правды для **ручного** закрытого выпуска `0.1.0`.
