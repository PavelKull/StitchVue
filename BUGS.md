## Баги и ошибки

### B-001 — кнопка «вниз» не доезжает до конца папки, пока листинг не готов
- **Статус:** открыто
- **Технический статус:** CONFIRMED · уверенность high
- **Где:** галерея, кнопка прыжка вверх/вниз (`GalleryScrollJumpButton`)
- **Что происходит:** сразу после открытия папки нажатие «вниз» опускает только на уже построенную высоту сетки (просмотренный / уже опубликованный префикс). Конец папки ещё не в `scrollHeight`, поэтому прыжок останавливается «на середине» будущей ленты.
- **Ожидание:** по нажатию «вниз» гарантированно оказаться у реального конца папки, даже если сканирование, метаданные и раскладка ещё не завершены.
- **Как повторить:**
  1. Открыть достаточно большую папку (листинг и сетка нарастают не мгновенно).
  2. Пока загрузка/инициализация не закончилась, нажать кнопку вниз.
  3. Оказаться не в конце папки, а на текущем низе уже отрисованного контента.
- **Код сейчас:** `jumpGalleryScroll` в `src/features/gallery/model/viewport/useGalleryScrollJump.ts` делает `scrollTo({ top: scrollHeight - clientHeight })` по **текущему** DOM. Высота растёт позже: `listingComplete={status === 'ready'}` в `GalleryPage` → `layoutMosaicPublished` / `publishedEnd` + `estimateUniformTail` в `widgets/gallery-grid/layout.ts`. Флага «хочу быть в конце» нет. Backend (`images-batch`, headers) высоту скролла не считает.
- **Причина:** подтверждена. Прыжок одноразовый; follow-max нет.
- **Как чинить:** прежняя рекомендация жива. Не ждать полной готовности. Намерение `pendingScrollToEnd`: клик сразу на текущий max → на росте `scrollHeight` снова `scrollTop = max`, пока флаг жив; снять при ready+низ / ручном скролле / «вверх» / смене папки. На время флага `behavior: 'auto'`. Спейсер на всё число файлов **не** первый шаг — ломает инкрементальную раскладку.
- **Зависимости:** B-011 — follow-end без тайлов в хвосте mosaic даст пустой конец. Не ждать очередь миниатюр.
- **Приёмка:** большая папка, «вниз» до `ready` — в реальном конце ленты; «вверх» сразу; ручной скролл снимает приклеивание.
- **Диагностика:** не нужна сверх ручного сценария.

### B-002 — миниатюра не заполняет тайл, чёрные полосы пока грузится
- **Статус:** открыто
- **Технический статус:** LIKELY · уверенность medium
- **Где:** сетка галереи, пока рисуется первый/промежуточный thumb
- **Что происходит:** картинка не на всю ширину и высоту ячейки; по краям тёмные/чёрные полосы.
- **Ожидание:** слот сразу заполнен кадром (`cover`), без полей и без «подложки».
- **Как повторить:** открыть папку и смотреть тайлы в момент появления миниатюр, пока пайплайн ещё не дошёл до финального тира.
- **Код сейчас:** тайл `object-fit: cover`, img `inset: 0` (`StitchVueGrid.module.scss`). Пока нет `thumbs.get` — `.placeholder` на весь слот. Первый JPEG: `produce_jpeg` / `bitmap_for_tier` → `finish` + `apply_orientation` → `encode_jpeg` из RGB (**без EXIF**). `image-orientation` на `<img>` нет. `tilePhotoStyle` ставит `fill` только при нечётном `rotationQuarters` (это B-003).
- **Причина (факт vs гипотеза):** факт — кэш-JPEG печётся без тега Orientation; старое «WebView крутит первый emit» для cache-файла **устарело**. Гипотезы оставшегося симптома: (1) виден фон слота / placeholder до `<img>`; (2) чёрные поля **внутри** camera embedded preview; (3) расхождение heuristic `embedded_orientation` (см. B-004). `cover` сам letterbox не даёт.
- **Как чинить:** не переписывать пайплайн. Сначала ручная развилка: пустой слот vs поля в JPEG vs вспышка ориентации. Страховка CSS: `image-orientation: none`. Не монтировать img до decode. Не `fill` на обычном тайле. Если поля в embedded — не emit, пока bake согласован (вместе с B-004).
- **Зависимости:** визуально рядом с B-004; **не** тот же баг, что B-003.
- **Приёмка:** EXIF 6/8: первый кадр без полей слота; слот cover.
- **Диагностика:** 1–2 кадра с EXIF 6/8; DevTools: placeholder vs `<img>` vs пиксели JPEG.

### B-003 — после поворота в просмотрщике сетка не меняет пропорции, thumb растягивается
- **Статус:** открыто
- **Технический статус:** CONFIRMED · уверенность high
- **Где:** просмотрщик → поворот по часовой → назад в сетку
- **Что происходит:** ячейка остаётся со **старым** aspect; миниатюра не пересобирается и **растягивается** в старый прямоугольник.
- **Ожидание:** слот и раскладка ряда/колонки учитывают `rotationQuarters`; bitmap без squash (cover + корректный CSS-rotate).
- **Как повторить:** открыть фото, повернуть, закрыть просмотрщик, найти тот же тайл.
- **Код сейчас:** `rotate_display_clockwise` (IPC) → `Pipeline` → `library::rotate_clockwise` (quarters в SQLite, JPEG не трогает). UI: `GalleryPage` + `metaVersion`. При `GEOMETRY_FIRST_LAYOUT` `geometryKey` **без** `metaVersion` (`StitchVueGrid.tsx`); `layoutMosaicPublished` передаёт предыдущий layout → `freezeUsedAspects` держит опубликованный aspect. `displayAspect` quarters видит; `tilePhotoStyle` при нечётном quarter — своп size + `objectFit: "fill"` (`displayRotation.ts`).
- **Причина:** подтверждена. Display-rotate поверх baked EXIF + заморозка mosaic. Не зависит от первого кадра B-002/B-004. Перекодировать thumb **не** нужно.
- **Как чинить:** прежняя рекомендация жива. При смене `rotationQuarters` у пути инвалидировать published geometry **этого индекса** (не весь каталог). Не `fill`: cover + своп width/height.
- **Зависимости:** не мешать bake EXIF (B-002/B-004). Не путать `viewerPhotoStyle` `fill` (B-009, fillScreen) с squash тайла.
- **Приёмка:** 90° — слот меняет пропорции, без squash; остальные кадры ряда не прыгают без нужды.
- **Диагностика:** не нужна.

### B-004 — пока thumb грузится, кадр сначала «повёрнут», потом встаёт нормально
- **Статус:** открыто
- **Технический статус:** LIKELY · уверенность medium
- **Где:** сетка, момент подмены первого preview на нормальный thumb
- **Что происходит:** вспышка ориентации «как с матрицы» / неверный 90°, затем разворот в правильное положение.
- **Ожидание:** любой показанный кадр уже в display-ориентации (EXIF уже в пикселях).
- **Как повторить:** папка с JPEG/HEIC/RAW, у которых EXIF Orientation ≠ 1; смотреть появление миниатюр.
- **Код сейчас:** JPEG 256: `produce_jpeg` сначала `embedded_jpeg` + `embedded_orientation`, затем полный decode (`pipeline/mod.rs`, `thumbnail/mod.rs`). Hover `decode_tile` — тот же embedded. Реэнкод без EXIF есть. CSS `image-orientation` нет.
- **Причина:** «браузер крутит по тегу, пока Rust не baked» для cache JPEG **слабо**. Остаётся heuristic `embedded_orientation` (thumb без тега / уже upright) и два emit (256 embedded → 512/полный). Не смешивать с пользовательским quarter (B-003).
- **Как чинить:** не отдавать 256, пока ориентация согласована с header; не emit embedded, если aspect/tag расходятся. Hover тот же путь. Регрессия: EXIF 1/3/6/8 и «уже upright» preview.
- **Зависимости:** B-002 (первый кадр), B-009 (тот же класс в viewer).
- **Приёмка:** нет вспышки «на боку» на EXIF 6/8; upright preview не переворачивается зря.
- **Диагностика:** сравнить первый `thumbnail-ready` 256 vs следующий тир на одном EXIF 6 файле.

### B-005 — в папке избранного миниатюры плохого качества
- **Статус:** открыто
- **Технический статус:** CONFIRMED · уверенность high
- **Где:** служебная папка избранного после добавления копий
- **Что происходит:** в избранном thumbs заметно хуже, чем те же кадры в исходной папке (мыло, апскейл мелкого preview).
- **Ожидание:** если оригинал уже был в сетке с нормальным тиром (512/1024), копия в избранном сразу показывает тот же кадр, без повторной «первой» 256-превьюхи.
- **Как повторить:** открыть альбом, дождаться нормальных миниатюр, добавить в избранное, открыть избранное.
- **Код сейчас:** ключ `identity_hash(path, size, mtime)` → `{hash}-{tier}.jpg`; lookup `cached_thumb(source_path, size, mtime, tier)` только по пути копии (`cache/mod.rs`). `favorite_snapshot_for_copy` есть и используется lifecycle/IPC (`favorite_origins_for_copies`), **pipeline кэш тиров origin не читает**. `file_ops` не клонирует строки `thumbnail_cache`.
- **Причина:** подтверждена. Связь origin↔copy на шаринг JPEG тиров не влияет. Копия → miss → decode с 256/embedded.
- **Как чинить:** прежняя схема жива, без новой SQLite-схемы. Лучше в момент copy: alias/hardlink тиров origin→copy (size + лучше sha256). Fallback при открытии избранного: miss copy → snapshot → `cached_thumb` origin → `emit_thumb` на path копии. Не стартовать с 256, если origin уже 512/1024. Не шарить при другом size; eviction — не удалять файл, пока жива хотя бы одна строка.
- **Зависимости:** C-005 только временем add; оптимистичное снятие не должно ждать eviction. Не трогать оригиналы фото.
- **Приёмка:** избранное сразу показывает ≥ origin tier при том же size; origin на диске не читается повторно, если JPEG тира есть.
- **Диагностика:** не нужна сверх ручного сравнения origin vs copy path в `thumbnail_cache`.

### B-006 — фон папки кажется тупящим; приоритеты в целом верные
- **Статус:** открыто
- **Технический статус:** UNVERIFIED как дефект; политика очереди CONFIRMED · уверенность low
- **Где:** пайплайн миниатюр, большая папка
- **Приоритет (продукт, не ломать):**
  1. **Viewport** — то, что сейчас на экране, всегда первое.
  2. **Новый экран при скролле** — кадры, которые только что въехали в кадр / ближайший overscan.
  3. **Оставшаяся ёмкость** — добивать остальную папку, чтобы к дальнейшему листанию уже были 256. Без скролла этот фон всё равно должен идти, а не ждать жеста.
- **Что происходит:** видимое в целом живое, но папка «на фоне» ощущается вялой. Туда-сюда по ленте — новые тайлы появляются охотнее, чем если сидеть на месте. Складывается впечатление, что очередь чуть тупит, а не что приоритеты перевёрнуты.
- **Как повторить:** большая папка, постоять на первом экране (хвост / прогресс). Потом поскроллить и сравнить, как быстро появляются ещё не виденные миниатюры.
- **Код сейчас:** `pick_index` (`pipeline/mod.rs`): P0 → headers pause → P1 holes → fair-share P5 каждые `FAIR_SHARE_EVERY=7` → Idle: **P4 upgrade, потом P2/P3**, иначе P5. `maintain_with` после idle-job если `!scrolling`. `FastScrolling` без P4, thumbs Map не чистит (не B-011).
- **Как подходить:** **не** переписывать планировщик и не инвертировать viewport-first. Сначала замерить `pipeline_stats` / idle: доля P4 vs P5. Если слоты в апгрейдах и P5 почти не стартает — чуть поднять долю фона / не держать `maintain_with` на crit path. Тесты `pick_index` idle/scroll/fast сохранить по смыслу.
- **Зависимости:** после B-007 (hover не должен отобрать фон). Не чинить «на глаз».
- **Приёмка:** viewport-first сохранён; фон папки идёт на Idle без скролла, с цифрами слотов до/после.
- **Диагностика:** обязательна. Стоять на 1 экране большой папки → лог приоритетов → скролл → сравнить.

### B-007 — hover-preload полного кадра как будто не работает
- **Статус:** открыто
- **Технический статус:** LIKELY · уверенность medium
- **Где:** сетка → наведение на тайл → клик в просмотрщик
- **Что происходит:** задумано: hover греет viewer-качество, открытие почти сразу. Сейчас после наведения и клика кадр всё равно **грузится** в просмотрщике.
- **Ожидание:** если курсор побыл на тайле достаточно, чтобы стартануть prefetch, открытие берёт уже тёплый кадр (или добивает тот же decode), а не начинает с нуля. Viewport-thumbs по-прежнему важнее hover (как B-006).
- **Как повторить:** дождаться миниатюр на экране, навести на фото, подождать долю секунды, открыть. Сравнить с кликом без наведения. RAW/JPEG отдельно.
- **Код сейчас:** механизм **есть**, не изобретать: `onHoverPhoto` → `enterPhoto` (`PHOTO_DELAY_MS = 100`) / `leavePhoto` (`LEAVE_GRACE_MS = 140`) в `hoverPrefetch.ts` + `galleryHover.ts` → `prefetch_photo` / `cancel_photo_prefetch`. Rust `viewer::prefetch` Join/Start; `grid_blocks_hover` режет hover при scroll / дырах 256 / headers. `peekPreloaded` только если `naturalWidth > 0` (`viewerPreload.ts`). Без native `ImageViewer` ставит `setOpening(true)`. Клик по тайлу шлёт `pointerleave` → `leavePhoto`.
- **Почему может «не работать» (проверить по месту):**
  1. Клик быстрее 100 ms — prefetch ещё не ушёл.
  2. `pointerleave` → cancel через 140 ms, как раз когда viewer должен забрать job.
  3. Decode в WebView не успел (`naturalWidth === 0`) → thumb + `setOpening(true)`.
  4. `grid_blocks_hover` + P4 держат слоты.
  5. Offer без native/sharp — в кэш только preview 256.
- **Как чинить:** склеить hover и open: не cancel открываемого path; если job идёт — Join; отдавать warm src без ожидания `naturalWidth`. Задержку 100 ms оставить от проезда; клик по тому же тайлу — сразу. Hover уступает P0/P1, не обязан обгонять фон папки.
- **Зависимости:** B-006 (слоты), B-009 (частота сырого thumb). C-006 расширяет то же `kept`/`prefetch_photo` — сначала склеить hover/open, не плодить второй preload.
- **Приёмка:** после hover ≥100 ms открытие без полной загрузки с нуля (JPEG); viewport-дыры по-прежнему важнее hover.
- **Диагностика:** сравнить клик сразу vs после 300 ms hover; RAW отдельно.

### B-008 — зум нижней панели не меняет размер единственной фотографии в app-fullscreen
- **Статус:** открыто
- **Технический статус:** LIKELY · уверенность medium
- **Где:** сетка, ползунок масштаба в нижней панели (`BottomControlBar`). Не зум просмотрщика.
- **Что происходит:** в папке остался **один** кадр (сценарий: несколько в локальную корзину, восстановлены все кроме одного). Ползунок ездит влево-вправо, **визуальный масштаб тайла не меняется**.
- **Проявляется только** если окно развёрнуто **кнопкой полноэкрана нижней панели** (`appFullscreen` / `setFullscreen`). В оконном режиме с тем же одним кадром зум, по словам, живой. Не путать с обычным maximize Windows, пока не проверено отдельно.
- **Ожидание:** `rowsPerScreen` (шаги `ZOOM_STEPS`) меняет размер единственного тайла и в fullscreen, в разумных пределах экрана (не больше viewport).
- **Как повторить:**
  1. Папка с несколькими фото, часть в «Удалённые», восстановить все кроме одной — в папке (или в корзине) один файл.
  2. Полноэкран нижней панели.
  3. Двигать зум — тайл как будто застыл.
- **Код сейчас:** `rowsPerScreen` входит в `geometryKey`. `fsLayoutFreeze` только `preparing`/`switching`, сброс на `settling`/`idle` (`GalleryPage` + `appFullscreenController`). Last-row mosaic: `placeRow` при `last && (natural > viewportHeight || natural < hTarget * 0.5)` ставит `height = min(hTarget, viewportHeight)` (`layout.ts`). Freeze как «залипание» маловероятен после сброса phase.
- **Как чинить:** не отключать зум при `images.length === 1`. Сначала режим (mosaic/grid/columns) и живые `tile.width`/`row.height` в FS vs окно. Если state меняется, а боксы нет — last-row / freeze; если боксы меняются, а на экране нет — CSS/FLIP. Не путать с B-009.
- **Зависимости:** нет с B-009.
- **Приёмка:** 1 фото + app-FS: шаги зума меняют размер тайла, не больше viewport; многофото-зум не регрессирует.
- **Диагностика:** обязательна. Сравнить `tile.width`/`row.height` на шагах слайдера в FS vs окне.

### B-009 — в просмотрщике при быстром листании кадр мелкий и «на боку», потом вырастает
- **Статус:** открыто
- **Технический статус:** LIKELY · уверенность medium
- **Где:** просмотрщик, листание фото (клавиши / жест), особенно быстро
- **Что происходит:** пока полный кадр не приехал, превью **не на весь экран**, потом увеличивается. В этот же момент картинка **повёрнута не так**, как должна; после загрузки встаёт размер и ориентация.
- **Ожидание:** любой показанный кадр (хоть 256) уже в **верной ориентации** и в геометрии «по экрану» (`fillScreen`: вертикаль на высоту / горизонталь на ширину). Мыло допустимо. Пустой центр / letterbox / переворот на время загрузки — нет.
- **Как повторить:** открыть сетку → просмотрщик → быстро листать папку с EXIF 6/8 или RAW. Смотреть первый кадр каждой смены файла.
- **Код сейчас:** смена `file.path`: warm native → иначе preview/grid-thumb + `setOpening(true)` (`ImageViewer.tsx`). `object-fit: contain`. Рамка `computeViewerFrame`; `aspectFromMeta` без quarters и **1**, если нет размеров (`viewerFrame.ts`). `syncDisplayAspect` quarters учитывает. `fillScreen` по умолчанию true. `data-layout-animate` анимирует рост.

### C-006 — приоритетная предзагрузка соседних фотографий в ImageViewer
- **Статус:** нужна правка
- **Технический статус:** CONFIRMED (разрыв vs уже существующее окно) · уверенность high
- **Где:** ImageViewer, последовательное листание и произвольный переход
- **Что происходит:** при просмотре N пользователь может видеть задержку, низкокачественный preview или ожидание следующего кадра. Соседи уже греются, но окно и качество не совпадают с целевым контрактом.
- **Ожидание:** при открытии N:
  - P0: N — абсолютный приоритет (текущий кадр).
  - P1: N+1 (или сосед по направлению навигации).
  - P2: следующие четыре (N+2…N+5 вперёд относительно направления).
  - P3: две назад (N−1…N−2), только когда high-pri обеспечены или есть свободные слоты.
  Окно пересчитывается на каждом переходе. Уже готовые ресурсы не запрашивать снова. Качество — полезное для текущего масштаба/HiDPI, не мыльный 256, если есть лучше. Полный RAW/HEIC decode не обязателен. Память ограничена; inflight Join; при jump устаревшие задачи уступают новому окну, кэш `kept` не сбрасывается целиком. Текущий кадр всегда важнее фона. Сетка viewport-first не голодает.
- **Как повторить (после реализации — приёмка):** открыть N → убедиться, что готовятся N+1…N+5; назад ниже приоритетом; переход на N+1 без повторного decode уже тёплого; быстрое листание без мыльного preview, если high-quality готов; резкий jump переключает окно; лимит памяти держит крупные кадры.
- **Код сейчас (reuse, не второй кэш):**
  - Текущий N: `ImageViewer` → `viewer_frame` + `viewerNeededEdge` (`viewerZoom.ts`).
  - Соседи FE: `GalleryPage` (~1760) → `preloadViewerNeighbors` (`viewerPreload.ts`) → `buildNeighborJobs` (`viewerPreloadLogic.ts`) + `set_viewer`.
  - Окно сейчас: вперёд `ahead` = 4 / 5 / **12** (`viewerPace.ts`), назад всегда 2; очередь = весь forward, потом back. `near` = первые **два** вперёд; при `fast` (`<180 ms`) `near=[]` → даже N+1 садится на grid-thumb.
  - Качество far: `resolveNeighborSource` принимает **любой** `thumbs` Map (часто 256). Near: `viewer_source` native или prepared 1024/512/256. Hover (B-007): отдельно `prefetch_photo` + `viewerNeededEdge(window)`.
  - Inflight: `kept` / `isReadyKept` / `generation`; полный reset только `cancelViewerPreload({ clearCache: true })` на смене папки. `MAX_ACTIVE=2`, `MAX_KEPT=8`.
  - Rust: `set_viewer` двигает **grid 256/512** (`viewer_steps` в `pick_index`), не `encode_viewer`. Hover/open Join — `pipeline/hover.rs::photo_action`. `grid_blocks_hover` и `viewer_wants_read` защищают viewport; P0/P1 сетки не yield из‑за viewer read.
- **Причина разрыва:** механизм есть, контракт C-006 нет. Слиты P1 и P2 (`near` = N+1 **и** N+2). Fast режет native у N+1. Far остаётся на 256. P3 не ждёт spare. Ahead=12 на fast шире, чем N+1…N+5. Соседи не Join в hover-слот.
- **Решение (зафиксировано 2026-10-19, для Spec-Kit 003):**
  1. Не создавать новую подсистему предзагрузки ImageViewer.
  2. Использовать существующие `preloadViewerNeighbors`, `buildNeighborJobs`, `viewerPreloadLogic.ts`, `viewerPreload.ts`.
  3. Не переписывать `pick_index`.
  4. Не создавать второй кэш.
  5. Порядок: сначала B-007 (join hover/open/viewer), затем C-006, затем оставшаяся часть B-009.
  6. P1 = N+1 (сосед по направлению), P2 = N+2…N+5, P3 = N−1…N−2.
  7. Быстрая навигация не сбрасывает приоритет ближайшей следующей фотографии (`near` не обнулять на fast).
  8. При смене направления учитывать фактическое движение; текущий кадр остаётся абсолютным приоритетом.
  9. Предыдущие кадры (P3) получают ресурсы после high-pri задач.
  10. Не менять `MAX_ACTIVE=2` без измерений.
  11. Не увеличивать безусловно `MAX_KEPT=8`; сначала проверить фактическую стоимость удерживаемых кадров.
  12. Не декодировать оригинальные RAW/HEIC в максимальном разрешении без необходимости.
  13. Viewport-загрузка основной галереи важнее фонового viewer-prefetch.
  14. Targeted-тесты: быстрая навигация, смена направления, reuse inflight, ограничение памяти.
- **Не делать:** новый disk cache; параллельные decode-слоты; native на весь P2; полный RAW/HEIC для far; сброс `kept` на каждый next; rewrite планировщика сетки.
- **Зависимости:** **после B-007** (glue hover/open/Join). **Затем** оставшаяся часть B-009 (рамка/fillScreen). Ориентация первого байта — B-002/B-004. Не ухудшать B-006.
- **Приёмка:**
  1. Открытие N готовит N+1…N+5.
  2. N−1/N−2 ниже приоритетом.
  3. Переход на N+1 без повторной загрузки готового.
