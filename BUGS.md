# Журнал багов, ошибок и правок

Черновик для этого чата: сюда записываем всё, что найдено в приложении, пока чат открыт.

Статусы: `открыто` · `нужна правка` · `закрыто`

---

## Баги и ошибки

### B-001 — кнопка «вниз» не доезжает до конца папки, пока листинг не готов
- **Статус:** открыто
- **Где:** галерея, кнопка прыжка вверх/вниз (`GalleryScrollJumpButton`)
- **Что происходит:** сразу после открытия папки нажатие «вниз» опускает только на уже построенную высоту сетки (просмотренный / уже опубликованный префикс). Конец папки ещё не в `scrollHeight`, поэтому прыжок останавливается «на середине» будущей ленты.
- **Ожидание:** по нажатию «вниз» гарантированно оказаться у реального конца папки, даже если сканирование, метаданные и раскладка ещё не завершены.
- **Как повторить:**
  1. Открыть достаточно большую папку (листинг и сетка нарастают не мгновенно).
  2. Пока загрузка/инициализация не закончилась, нажать кнопку вниз.
  3. Оказаться не в конце папки, а на текущем низе уже отрисованного контента.
- **Код сейчас:** `jumpGalleryScroll` в `useGalleryScrollJump.ts` делает `scrollTo({ top: scrollHeight - clientHeight })` по **текущему** DOM. Высота сетки растёт позже (`listingComplete={status === 'ready'}`, инкрементальный `publishedEnd` в layout). Флага «хочу быть в конце» нет — после догрузки скролл сам не догоняет.
- **Как чинить (черновик):** не ждать полной готовности перед прыжком. Завести **намерение «приклеиться к концу»** (`pendingScrollToEnd`):
  1. Клик «вниз» сразу скроллит на текущий max и ставит флаг, пока листинг/раскладка не `ready`.
  2. На каждом росте `scrollHeight` (листинг, метаданные, `publishedEnd`) снова ставить `scrollTop = max`, пока флаг жив.
  3. Снять флаг, когда папка готова **и** мы уже у низа; также снять, если пользователь скроллит сам, нажимает «вверх» или меняет папку.
  4. Прыжок «вверх» не должен ждать догрузки.
  Альтернатива — заранее резервировать высоту по числу файлов (спейсер). Это тяжелее и ломает текущую инкрементальную раскладку; для гарантии «вниз» достаточно follow-max.
- **Заметки:** smooth-скролл к устаревшему max может обогнать догоняющие прыжки — на время флага лучше `behavior: 'auto'`. Не путать конец **листинга** с концом **очереди миниатюр**: скроллить надо к последнему слоту сетки, а не ждать все thumbs.

### B-002 — миниатюра не заполняет тайл, чёрные полосы пока грузится
- **Статус:** открыто
- **Где:** сетка галереи, пока рисуется первый/промежуточный thumb
- **Что происходит:** картинка не на всю ширину и высоту ячейки; по краям тёмные/чёрные полосы.
- **Ожидание:** слот сразу заполнен кадром (`cover`), без полей и без «подложки».
- **Как повторить:** открыть папку и смотреть тайлы в момент появления миниатюр, пока пайплайн ещё не дошёл до финального тира.
- **Гипотеза:** полосы — это фон тайла (`background: var(--elevated)` / flatten `[0x1b, 0x1f, 0x25]`), а не рамка в JPEG. `object-fit: cover` сам по себе letterbox не даёт; поля появляются, если **коробка img и пиксели расходятся** (EXIF `image-orientation` в WebView2 vs уже подобранный aspect слота, CSS `transform` без свопа размеров, встроенный preview с полями). Пока мета ещё 3:2 (`ESTIMATED_ASPECT`), а bitmap уже другой — при `cover` скорее кроп, не поля; значит смотреть ориентацию первого кадра, не только aspect.
- **Связь:** тот же первый кадр, что и B-004; чинить пайплайн ориентации вместе. Не путать с B-003 (ручной поворот в просмотрщике).
- **Как чинить (черновик):** первый emit в кэш — уже **baked** JPEG без EXIF Orientation; на `<img>` явно `image-orientation: none`, если печём сами. Не показывать кадр, пока ориентация не применена. Не оставлять `object-fit: fill` на тайле.

### B-003 — после поворота в просмотрщике сетка не меняет пропорции, thumb растягивается
- **Статус:** открыто
- **Где:** просмотрщик → поворот по часовой → назад в сетку
- **Что происходит:** ячейка остаётся со **старым** aspect; миниатюра не пересобирается и **растягивается** в старый прямоугольник.
- **Ожидание:** слот и раскладка ряда/колонки учитывают `rotationQuarters`; bitmap без squash (cover + корректный CSS-rotate).
- **Как повторить:** открыть фото, повернуть, закрыть просмотрщик, найти тот же тайл.
- **Код сейчас:** `rotate_display_clockwise` пишет quarters и поднимает `metaVersion`. `displayAspect` и `tilePhotoStyle` это видят. Но при `GEOMETRY_FIRST_LAYOUT` ключ геометрии **без** `metaVersion`, в mosaic/columns предыдущий layout передаётся дальше, `freezeUsedAspects` **замораживает** уже опубликованные слоты. CSS крутит img, размер ячейки тот же. Для нечётного quarter `tilePhotoStyle` ставит `objectFit: "fill"` — отсюда squash.
- **Это отдельный баг:** ручной display-rotate поверх baked EXIF, плюс заморозка mosaic. Не зависит от «первого кадра» B-002/B-004.
- **Как чинить (черновик):** при смене `rotationQuarters` у пути инвалидировать published geometry **этого индекса** (не весь каталог). Не `fill`: cover + своп width/height как сейчас для 90°. Кэш JPEG можно не перекодировать — достаточно layout + CSS.

### B-004 — пока thumb грузится, кадр сначала «повёрнут», потом встаёт нормально
- **Статус:** открыто
- **Где:** сетка, момент подмены первого preview на нормальный thumb
- **Что происходит:** вспышка ориентации «как с матрицы» / неверный 90°, затем разворот в правильное положение.
- **Ожидание:** любой показанный кадр уже в display-ориентации (EXIF уже в пикселях).
- **Как повторить:** папка с JPEG/HEIC/RAW, у которых EXIF Orientation ≠ 1; смотреть появление миниатюр.
- **Гипотеза:** быстрый путь (embedded JPEG / preview) и полный `finish()` + `apply_orientation` расходятся. Браузер ещё крутит по тегу (`image-orientation: from-image`), а слот уже по oriented `width`/`height` из header — визуально «лежит на боку» и с полями (B-002). Второй файл в кэше без тега — картинка «встаёт». `embedded_orientation` как раз про этот класс ошибок (thumb без тега / уже upright).
- **Связь:** с B-002 часто один корень (первый кадр). С B-003 не смешивать: там пользовательский quarter после ready.
- **Как чинить (черновик):** не отдавать во frontend JPEG с Orientation ≠ 1. Ориентацию применять до первого `emit_encoded`. Проверить hover + `produce_jpeg` embedded path. Регрессия: EXIF 1/3/6/8 и «уже upright» preview.

### B-005 — в папке избранного миниатюры плохого качества
- **Статус:** открыто
- **Где:** служебная папка избранного после добавления копий
- **Что происходит:** в избранном thumbs заметно хуже, чем те же кадры в исходной папке (мыло, апскейл мелкого preview).
- **Ожидание:** если оригинал уже был в сетке с нормальным тиром (512/1024), копия в избранном сразу показывает тот же кадр, без повторной «первой» 256-превьюхи.
- **Как повторить:** открыть альбом, дождаться нормальных миниатюр, добавить в избранное, открыть избранное.
- **Почему так:** кэш **не про пиксели файла**, а про путь. Ключ `source_path + size + mtime` (`thumbnail_cache`, `identity_hash` → имя `{hash}-{tier}.jpg`). Копия — другой путь и обычно другой mtime, даже при тех же байтах. Lookup в пайплайне идёт только по пути копии → miss → заново decode. Первый emit часто **256 / embedded JPEG** (крошечный camera-preview), пока очередь не догонит 512/1024. Связь origin↔copy в `favorite_copies` (есть `origin_path`, `content_sha256`) на кэш миниатюр **не влияет**.
- **Можно ли не декодировать копию снова:** да, если origin и copy совпадают по size (и лучше sha256) и у origin уже есть файлы тиров.
  1. **Лучше всего — в момент add to favorites:** для каждого тира origin вставить строки кэша/meta на identity копии. Файл JPEG: hardlink или тот же `thumbnail_path` на две строки (при eviction — не удалять, пока жива хотя бы одна). Не ждать открытия избранного.
  2. **Fallback при открытии избранного:** miss по copy → `favorite_snapshot_for_copy` → `cached_thumb` origin → сразу `emit_thumb` на path копии; decode копии только если origin miss или size/hash разошлись.
  3. Не копировать в избранное «с нуля» 256, если origin уже отдал 512/1024 — иначе снова мыло до второго прохода.
- **Ограничения:** не шарить кэш, если copy size ≠ origin (файл дописали). Trash/rename origin — кэш origin может протухнуть; тогда обычный decode копии. Не читать пользовательский оригинал с диска второй раз, если JPEG тира уже на диске кэша.

### B-006 — фон папки кажется тупящим; приоритеты в целом верные
- **Статус:** открыто
- **Где:** пайплайн миниатюр, большая папка
- **Приоритет (продукт, не ломать):**
  1. **Viewport** — то, что сейчас на экране, всегда первое.
  2. **Новый экран при скролле** — кадры, которые только что въехали в кадр / ближайший overscan.
  3. **Оставшаяся ёмкость** — добивать остальную папку, чтобы к дальнейшему листанию уже были 256. Без скролла этот фон всё равно должен идти, а не ждать жеста.
- **Что происходит:** видимое в целом живое, но папка «на фоне» ощущается вялой. Туда-сюда по ленте — новые тайлы появляются охотнее, чем если сидеть на месте. Складывается впечатление, что очередь чуть тупит, а не что приоритеты перевёрнуты.
- **Как повторить:** большая папка, постоять на первом экране (хвост / прогресс). Потом поскроллить и сравнить, как быстро появляются ещё не виденные миниатюры.
- **Не считать сразу поломкой планировщика.** P0/P1 на viewport и nearby при скролле, скорее всего, уже правильные (`pick_visible_missing`, `Scrolling`/`FastScrolling`). Смотреть, **не съедает ли хвост** лишняя работа, когда экран уже с превью: Idle сразу гоняет P4 (512/1024 тех же видимых), P5 только раз на 7 некритичных ходов, `maintain_with` на каждый idle-job. Это может быть ок как политика «качество экрана важнее», и тогда правка минимальная (доля фона, не держать maintain на crit path), а не смена порядка «сначала вся папка, потом экран».
- **Как подходить к правке:** сначала замерить/проследить, чем заняты read slot в Idle после готовности viewport. Если слоты в апгрейдах и P5 почти не стартает — чуть поднять долю фона, не трогая (1) и (2). Не переписывать приоритеты «видимое неважно». Тесты pick_index idle/scroll/fast сохранить по смыслу viewport-first.

### B-007 — hover-preload полного кадра как будто не работает
- **Статус:** открыто
- **Где:** сетка → наведение на тайл → клик в просмотрщик
- **Что происходит:** задумано: hover греет viewer-качество, открытие почти сразу. Сейчас после наведения и клика кадр всё равно **грузится** в просмотрщике.
- **Ожидание:** если курсор побыл на тайле достаточно, чтобы стартануть prefetch, открытие берёт уже тёплый кадр (или добивает тот же decode), а не начинает с нуля. Viewport-thumbs по-прежнему важнее hover (как B-006).
- **Как повторить:** дождаться миниатюр на экране, навести на фото, подождать долю секунды, открыть. Сравнить с кликом без наведения. RAW/JPEG отдельно.
- **Механизм уже есть, не изобретать заново:** `onHoverPhoto` → `enterPhoto` (задержка `PHOTO_DELAY_MS = 100`) → `prefetch_photo` → `rememberPreloaded` / `viewer-frame-ready` → при открытии `peekPreloaded`. Это и есть исходный замысел.
- **Почему может «не работать» (проверить по месту, не ломать пайплайн):**
  1. Клик быстрее 100 ms — `prefetch-photo` ещё не ушёл.
  2. Клик шлёт `pointerleave` → `leavePhoto` → через `LEAVE_GRACE_MS` (140) `cancel_photo_prefetch` и `pendingHover = null` — как раз когда просмотрщик должен забрать тот же job.
  3. `peekPreloaded` отдаёт кадр только если `naturalWidth > 0`. Decode в WebView не успел — viewer падает на thumb и качает заново (`setOpening(true)`).
  4. Rust `grid_blocks_hover`: slot hover не берётся, пока скролл / нет 256 на видимых / headers. Плюс P4 апгрейды держат `read_slots` — hover ждёт за апгрейдом сетки.
  5. Offer без `nativePath`/`sharpPath` — в кэш кладётся только preview 256, в зрителе всё равно «загрузка» большого кадра.
- **Как подходить:** не новый прелоад. Склеить hover и open: не cancel’ить prefetch открываемого пути; если job уже идёт — Join, не Start заново; отдавать в viewer ещё не дорисованный warm src. Задержку 100 ms оставить от случайных проездов, но клик по тому же тайлу должен стартовать сразу. Hover по-прежнему уступает дырам viewport (P0/P1), не обязан обгонять фон папки.

### B-008 — зум нижней панели не меняет размер единственной фотографии в app-fullscreen
- **Статус:** открыто
- **Где:** сетка, ползунок масштаба в нижней панели (`BottomControlBar`). Не зум просмотрщика.
- **Что происходит:** в папке остался **один** кадр (сценарий: несколько в локальную корзину, восстановлены все кроме одного). Ползунок ездит влево-вправо, **визуальный масштаб тайла не меняется**.
- **Проявляется только** если окно развёрнуто **кнопкой полноэкрана нижней панели** (`appFullscreen` / `setFullscreen`). В оконном режиме с тем же одним кадром зум, по словам, живой. Не путать с обычным maximize Windows, пока не проверено отдельно.
- **Ожидание:** `rowsPerScreen` (шаги `ZOOM_STEPS`) меняет размер единственного тайла и в fullscreen, в разумных пределах экрана (не больше viewport).
- **Как повторить:**
  1. Папка с несколькими фото, часть в «Удалённые», восстановить все кроме одной — в папке (или в корзине) один файл.
  2. Полноэкран нижней панели.
  3. Двигать зум — тайл как будто застыл.
- **Гипотезы (не ломать зум многофото):**
  1. Mosaic + `fit === 0`: высота ряда часто `natural = width/aspect`. На большом fullscreen-viewport срабатывает last-row (`natural > viewportHeight` → `height = min(hTarget, viewport)`), либо наоборот все шаги упираются в ширину/высоту экрана и выглядят одинаково. В окне с сайдбаром пропорции другие — зум заметен.
  2. На время `preparing`/`switching` сетка **замораживает** width/height (`fsLayoutFreeze`); если freeze/pending ResizeObserver зависает при одном файле — ключ геометрии меняется от `rowsPerScreen`, а измеренный viewport нет. На `settling`/`idle` freeze должен сбрасываться — проверить, что phase доходит.
  3. В fullscreen панели прячутся: viewport вырос, один кадр уже «на весь экран» на нескольких шагах зума.
- **Как подходить:** сначала режим раскладки (mosaic/grid/columns) и живые `tile.width`/`row.height` при движении слайдера в FS vs окно. Не отключать зум при `images.length === 1`. Если state `rowsPerScreen` меняется, а боксы нет — layout/freeze; если боксы меняются, а на экране нет — CSS/FLIP/object-fit.

### B-009 — в просмотрщике при быстром листании кадр мелкий и «на боку», потом вырастает
- **Статус:** открыто
- **Где:** просмотрщик, листание фото (клавиши / жест), особенно быстро
- **Что происходит:** пока полный кадр не приехал, превью **не на весь экран**, потом увеличивается. В этот же момент картинка **повёрнута не так**, как должна; после загрузки встаёт размер и ориентация.
- **Ожидание:** любой показанный кадр (хоть 256) уже в **верной ориентации** и в геометрии «по экрану» (`fillScreen`: вертикаль на высоту / горизонталь на ширину). Мыло допустимо. Пустой центр / letterbox / переворот на время загрузки — нет.
- **Как повтотить:** открыть сетку → просмотрщик → быстро листать папку с EXIF 6/8 или RAW. Смотреть первый кадр каждой смены файла.
- **Гипотезы:** при смене `file.path` сразу ставят grid-thumb (`object-fit: contain` в рамке). Рамка считается из meta/aspect; если meta ещё 1:1 или без swap quarters — маленькое окно по центру, затем `data-layout-animate` анимирует рост. Thumb с EXIF / sensor-ориентацией даёт «на боку» (тот же класс, что B-002/B-004), viewer-кадр уже baked. Быстрый next рвёт neighbor preload (B-007) — снова сырой thumb.
- **Как чинить (два варианта, выбрать один продуктово):**
  1. **Предпочтительно:** не блокировать листать. Первый paint — thumb/preview, но рамка сразу от **известного display-aspect** (header meta + EXIF, не 1:1), `fillViewport`, ориентация уже в пикселях или через `viewerPhotoStyle`. Пока нет даже такого кадра — предыдущий файл или нейтральный fullscreen-placeholder, не «миниатюра в углу».
  2. **Жёстче:** не переключать файл, пока нет кадра, который можно растянуть на экран в верной ориентации (хотя бы 256). Риск: быстрый просмотр упирается в диск; тогда нужен явный лимит ожидания и всё равно (1) как fallback.
- **Связь:** ориентация первого байта — с B-002/B-004; тёплый кадр к открытию — с B-007. Не путать с зумом сетки B-008.

### B-010 — при смене языка прыгает высота модалки
- **Статус:** открыто
- **Где:** в первую очередь Настройки (язык на вкладке интерфейса). Проверить и остальные диалоги с `height: auto`.
- **Что происходит:** переключение ru/en/de/zh-Hans меняет длину строк → оболочка окна **скачет по высоте**.
- **Ожидание:** пока диалог открыт, его высота **стабильна** при смене языка. Текст переносится или скроллится внутри панели, рамка не дёргается.
- **Как повторить:** Настройки → язык, несколько раз сменить локаль, не закрывая окно. Смотреть край диалога.
- **Код сейчас:** `.dialog { height: auto; max-height: min(80vh, …) }`. У панелей есть `max-height`, чтобы неактивные вкладки не раздували окно, но **нижней** высоты нет — короче копирайт = ниже окно.
- **Как чинить (черновик):** зафиксировать высоту шелла (например `height: min(80vh, …)` или min-height = текущему max). Контент — `overflow-y: auto` в pane. Не разносить вкладки разной «естественной» высотой. Сверить ru/en/de/zh-Hans на одной вкладке. Скрин в `ui-catalog/modals/` (C-002) до/после.

### B-011 — быстрый скролл / прыжок вниз: миниатюры пропадают, потом вспыхивают пачкой
- **Статус:** открыто
- **Где:** сетка уже **полностью** прогретая (лоудер на кнопке вверх-вниз погас), быстрый скролл вверх-вниз или прыжок в конец
- **Что происходит:** какое-то время тайлы без картинок (или сетка миниатюр **пропадает целиком**), затем все thumbs появляются сразу. Это не «холодный» decode папки.
- **Ожидание:** если JPEG тира уже в кэше, при входе в кадр img показывается сразу (или с крошечной задержкой WebView). Не пустой экран на быстром скролле и не пачка на весь viewport разом после паузы.
- **Как повторить:** открыть большую папку, дождаться конца лоадера, погонять скролл / «вниз». Смотреть пустые слоты и мигание всей ленты.
- **Куда смотреть (пока не чинить):**
  1. **Виртуализация:** `rowsCovering` только ~1 экран вверх и 2 вниз. Прыжок на низ размонтирует старые `<img>` и монтирует новые — WebView2 может отложить decode пачки `convertFileSrc`. Кэш Rust тут ни при чём.
  2. **Хвост mosaic:** unpublished / estimated spacer без тайлов (GEOMETRY_FIRST). Прыжок в «низ» скролла = пустое место, потом publish — все слоты сразу. Связь с B-001, но даже при готовых thumbs.
  3. **React:** `thumbs` Map + редкий `thumbVersion`/`paintVersion` — если события кэша копятся, один setState рисует сотню img за кадр.
  4. **FastScrolling:** планировщик не должен *прятать* уже известные thumbs; если UI пустой при тёплом Map — это фронт (окно рядов / CSS), не P5.
- **Не делать сейчас:** не поднимать параллелизм HDD и не отключать виртуализацию «на всякий». Сначала: пустые слоты при ненулевом `thumbs.get(path)` vs нет тайлов в layout vs img есть, но blank. Потом точечно: чуть шире overscan, не размонтировать img в окне, или placeholder из уже известных src.

## Правки (не обязательно баги)

### C-001 — один шаблон для загрузки, пустой папки и «нет подходящих файлов»
- **Статус:** нужна правка
- **Где:** центр `galleryLayer` при открытии папки / пустом содержимом
- **Что сейчас:** сообщения разъехались по двум визуалам и двум веткам логики.
  - Загрузка / геометрия: одна строка `styles.message` + `common.opening` («Открытие…»). `common.loading` («Загрузка…») рядом не используется.
  - Ошибка скана: тоже `styles.message`, сырой `error`.
  - Пустая обычная папка и «нет поддерживаемых форматов»: каркас `emptyGallery` (иконка + title + description) через `resolveGalleryEmptyKind`.
  - Избранное / корзина пустые: снова `styles.message` и отдельные ключи `emptyFavorites` / `emptyTrash`. В `resolveGalleryEmptyKind` при любом `serviceRole` сразу `'none'` — каркас не берётся.
  - В i18n уже есть `gallery.subfoldersOnly`, в kind его нет: папка только с подпапками не показывает этот шаблон.
- **Что изменить:** один набор состояний и один layout (как `emptyGallery`): загрузка (листинг/геометрия), пусто, нет поддерживаемых файлов, только подпапки, пустое избранное, пустая корзина, ошибка открытия. Сканирование не должно выглядеть «голым» текстом с многоточием, если для пустоты уже есть нормальный шаблон. Kind расширить, служебные папки не выкидывать в `'none'` ради отдельного `<p>`.
- **Зачем:** сейчас при открытии папки мелькает другое сообщение, чем когда папка реально пуста — ощущение черновика, а не одной системы пустых экранов. Не баг масштаба/данных, а единообразие UX. Не смешивать с B-006 (скорость thumbs): это копирайт и вёрстка placeholder’а.

### C-002 — систематизировать тосты, оповещения об ошибках и модалки
- **Статус:** нужна правка
- **Где:** вся оболочка: файловые операции, загрузка папки, настройки, корзина/избранное, свойства, rename, confirm
- **Что сейчас:** три канала без общей карты «когда что»:
  - **Тост / notice:** `OperationNoticeView` + `fileNotice` (успех / partial / failed, undo). Рядом `bootNotice` — отдельный `<p>` в галерее, не тост. `common.errorToast` в каталоге есть, живой единый тост-хост не виден.
  - **Ошибки:** `localizeErrorCode` / `formatInvokeError` в одних местах, сырой `error` / `notice.text` в других. Restore-коды идут в `ConfirmMoveDialog`, сбой скана — в `styles.message` (см. C-001).
  - **Модалки:** много копий одного паттерна (`useAnimatedModal` + свой backdrop): Settings, Rename, TrashFolderDelete, PhotoProperties, SupportReminder, FavoriteTrashUnfavorite, ConfirmMove (ещё и из Settings). Нет общего shell (заголовок, кнопки, фокус, Esc, слой).
- **Что изменить:** явная шкала: тост (короткий итог операции, авто-скрыть, undo) / модалка (решение: конфликт имени, подтверждение удаления) / полноэкранный empty (C-001, не тост). Один визуал тоста и один каркас диалога; коды ошибок только через i18n. Не плодить третий вид «полоска над сеткой».
- **Визуальный каталог (чтобы править на глаз):** в корне репозитория папка **`ui-catalog/`** — скриншоты всех всплывающих и пустых состояний, не живые пользовательские фото.
  - Подпапки: `toasts/`, `modals/`, `empty/` (C-001), плюс `index.md`: ситуация → файл PNG.
  - Снимать **фикстуры** (заголовок, текст, кнопки, тон success/partial/failed), не галерею на 50k. Один кадр на кейс, ru (и en, если копирайт расходится).
  - Сначала страница-каталог на существующих виджетах (`OperationNoticeView`, ConfirmMove, Settings, Rename, emptyGallery…) с захардкоженными пропсами — без новой UI-библиотеки.
  - Скриншоты: по желанию скрипт. **Playwright** — кандидат только как генератор PNG из каталога (`INVESTIGATE`, не ставить в этом этапе: отдельный браузер ≠ WebView2, дерево зависимостей тяжёлое). **Storybook/Chromatic не брать** ради этой задачи (лишний runtime). Пока каталог маленький — ручной снимок с той же страницы допустим.
  - В git: либо эталонные PNG как спецификация вида, либо `.gitignore` на `ui-catalog/**/*.png` и в репо только `index.md` + скрипт; решить при первом коммите каталога.
- **Зачем:** иначе одна и та же ошибка выглядит то строкой, то диалогом, то notice — и сложно решать, куда класть новый кейс. Каталог скринов даёт сверку всех ситуаций сразу. Это UX-система, не отдельный crash. Связано с C-001, не смешивать с логикой избранного/корзины.

### C-003 — замокать UI обновления (кнопка + диалог), по плану апдейтера
- **Статус:** нужна правка
- **Где:** всплывающий диалог + постоянная точка входа. Спека: `specs/002-stitchvue-release-auto-update/` (ещё не в коде). Каталог скринов — C-002 `ui-catalog/modals/`.
- **Как задумано в 002 (не выдумывать другой продукт):**
  - Проверка **один раз при запуске** (`check()`), не таймер.
  - Модалка: новая версия, release notes, **«Обновить»** / **«Позже»**. Без автоустановки. «Позже» — до следующего запуска, без скачивания.
  - «Обновить» **неактивно** при файловой операции / unfavorite (gate), с коротким объяснением.
  - Прогресс скачивания в том же диалоге; ошибка сети — i18n, не сырой текст (C-002).
  - Модуль в плане: `src/features/app-update/` → `UpdateDialog.tsx`; вешать в `App.tsx`.
- **Куда кнопку (визуально):**
  1. **Главное** — сам диалог (как в spec). Это и есть «нажать и обновиться».
  2. **Постоянный вход** — Настройки → О программе, рядом с версией (`AboutPanel` уже показывает `getVersion`). Кнопка «Обновить…» / «Доступна vX.Y.Z» открывает тот же диалог, если пользователь закрыл «Позже». Не плодить вторую панель на нижней панели галереи.
  3. Опционально тонкий бейдж на шестерёнке — только если диалог на старте слишком легко пропустить; не делать основным.
- **Сейчас, без плагина:** не ждать GitHub/`tauri-plugin-updater`. Фикстура: «установлено 0.1.0, доступно 0.2.0», notes-заглушка, состояния: доступно / качается (прогресс) / ошибка / занято file op. Дев-флаг или пункт в ui-catalog, чтобы открыть диалог в любой момент и посмотреть вид. Боевой `check()` не звать.
- **Зачем:** релизный апдейтер в спеке есть, в UI дыра; нужен макет «куда жать», пока CI и подпись не готовы. Не смешивать с установкой NSIS и ключами. Когда 002 поедет — подменить mock на `checkForUpdate` / `downloadUpdateWithProgress` / `installUpdate`.

### C-004 — вкладка «Поддержать»: звезда GitHub и визуал кнопок
- **Статус:** нужна правка
- **Где:** Настройки → вкладка support (`SupportPanel`): карточки CloudTips / Boosty, чекбокс не напоминать. Не путать с About (там уже репозиторий без акцента на star).
- **Что сейчас:** две карточки с заголовком, текстом и голой `primaryAction` без иконок. GitHub на этой вкладке нет. Выглядит плоско, «поблагодарить» не цепляет взгляд.
- **Что изменить:**
  1. Сначала нарисовать/посмотреть текущий вид (скрин в `ui-catalog/modals/` — C-002).
  2. Добавить заметное действие **«Поставить звезду на GitHub»** (или короче): иконка звезды, акцент сильнее донатов-ссылок или отдельная третья карточка. URL — репозиторий `githubRepo` из `external-links.json` (`openExternalLink`). Не ставить звезду через API, только открыть страницу репо.
  3. Всем кнопкам вкладки — иконки (CloudTips / Boosty / GitHub star / внешняя ссылка), единый ряд как `aboutAction`, но support может быть чуть ярче (heart/star). Не тащить сторонние логотипы, если нет лицензии — свои `StitchVueIcon`.
  4. i18n ru/en/de/zh-Hans. Не ломать hideReminders.
- **Зачем:** донат уже есть, не хватает бесплатного и заметного «звезда»; кнопки без иконок на фоне остального About выглядят бедно. UX вкладки, не пайплайн. C-003 (обновление) на About, это — support.

### C-005 — оптимистичный уход из избранного: не показывать папку, звёзды и выделение
- **Статус:** нужна правка
- **Где:** папка «Избранное», снятие копий (все / часть), сайдбар, сетка, звёзды, selection
- **Что сейчас:** массово убрать все из избранного → навигация в родителя есть (`navigateLocation`), но ещё какое-то время видна папка «Избранное» и **заполненные** звёзды. Частичное изъятие: копии и отметки живут, пока IPC не закончится. В `favoriteDisplayOn` при `inFavoritesFolder` звезда **всегда on** — overlay «desired: false» на этой папке не гасит иконку.
- **Что изменить:** сразу (оптимизм), фон — copy/remove:
  1. Снятые пути **пропадают из сетки** (и из просмотрщика), не ждать успеха FS.
  2. Звёзды этих путей — off везде (сетка, сайдбар избранного в альбоме).
  3. Выделение с них снять в том же тике.
  4. Если папка избранного после операции пустая (все сняли) — **сразу** UI родителя, плитку «Избранное» скрыть (`optimisticHiddenFolderKeys` уже есть). Саму пустую/полупустую служебную папку не держать на экране «пока удаляется».
  5. Откат overlay только если IPC failed (как сейчас success/error), не мигать избранным при успехе.
- **Не** ждать cleanup папки, чтобы сменить view. Не переписывать lifecycle избранного — дожать существующий optimistic overlay + landing (`massUnfavoriteStartLandingKey` / finish). Инварианты: оригинал не трогать; тесты `favorite*Optimistic*`, `removeFavoritesBatch`.
- **Зачем:** пользователь уже решил «убрать из избранного»; ждать диск и при этом видеть звёзды/папку — ощущение, что жест не принят. UX поверх уже заложенного оптимизма, не новый пайплайн.
